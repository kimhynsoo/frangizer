# RAG 서비스

Java 게이트웨이(:8080)의 내부 요청을 FastAPI(:8001)가 처리합니다. 상담은 LangChain + LangGraph 단일 에이전트이며, 레시피도 기존 `/rag-query`를 사용합니다. 별도 레시피 RDB·공개 API는 추가하지 않았습니다.

구현된 경로:

| 경로 | 인증 | 동작 |
|---|---|---|
| `POST /rag-query` | 서비스 토큰 + 원 사용자 JWT | 허용 판본 검색·상담 또는 구조화 레시피 응답 |
| `POST /internal/v1/index-jobs` | 서비스 토큰 | 202 작업 접수·동일 요청의 기존 상태 반환 |
| `GET /internal/v1/index-jobs/{job_id}` | 서비스 토큰 | 작업 상태 조회 |
| `GET /health` | 서비스 토큰 | 모델 설정·유효한 검색 산출물 준비 여부 |

현행 C 백엔드의 **같은 job_id로 POST를 반복하는 조회 방식**도 지원합니다. 후속 GET 조회로 전환해도 RAG 변경 없이 연결할 수 있습니다. `docs/api` 계약은 변경하지 않았습니다. 문서 상세의 `sections` 반환을 위한 새 내부 API는 아직 없습니다.

Python 3.11, Java 검사에는 Java 25를 사용합니다.

```bash

python3.11 -m venv .venv
```

외부 모델·임베딩 호출 없이 API, 그래프, 실제 PDF 추출·FAISS 생성/검색, 판본/권한 경계, 레시피 응답을 검사합니다. 기본 검사에서 실제 Java JWT 검사 3개는 건너뜁니다. 다음 절차로 Java까지 검사할 수 있습니다.

SWIG 확장 모듈의 알려진 초기화 경고 3종만 `pytest.ini`에서 제외하고 나머지 경고는 실패 처리합니다. FAISS import 시 이 경고를 일괄 `-W error`로 올리면 네이티브 확장 초기화가 비정상 종료할 수 있으므로 위 명령을 사용합니다.

## Java와 실제 HTTP 연동 검사

기존 서버·DB·`.env`를 사용하지 않습니다. 임시 H2, 임시 저장 폴더, 빈 포트를 사용하고 종료 시 정리합니다. 실제 Java 인증·업무 코드와 FastAPI·PDF·FAISS를 연결하되 임베딩은 테스트 대역이며 LLM 호출은 금지합니다.

```bash
cd /Users/inwoopark/workspace/ai-service/ai-service-project/frangizer/rag
source .venv/bin/activate
# macOS; 다른 OS에서는 설치된 Java 25의 JAVA_HOME을 지정
export JAVA_HOME=$(/usr/libexec/java_home -v 25)
export PATH="$JAVA_HOME/bin:$PATH"
mkdir -p .demo
../backend/gradlew -p ../backend \
  -I "$PWD/tests/java/classpath.init.gradle" -q testClasses ragInteropClasspath \
  > .demo/backend-classpath.txt
export FRANGIZER_JAVA_CP="$(tail -n 1 .demo/backend-classpath.txt)"
python -m pytest -q
python -m tests.backend_smoke
```

확인 범위: 역할별 Java JWT → PDF 업로드 → 승인 → 비동기 색인 → 기존 POST 폴링 → 배포 → 점주·본사 질문 → **20 mL / 출처 PDF 5쪽** → 같은 요청 재사용 → 예비 점주 접근 차단. 테스트 안에서 v1.1을 명시적으로 업로드·승인·배포하고, **2026-10-26 00:00 KST 전후 20→15 mL 전환**도 확인합니다. staged 폴더를 자동 색인하는 기능은 없습니다.

이 검사를 실제 임베딩 검색·LLM 상담 품질, MariaDB 또는 브라우저 E2E 통과로 해석하지 않습니다.

## 실행 전 점검

실제 API·DB 호출, 서버 시작, 색인 없이 설정과 경로만 확인합니다. 비밀값은 출력하지 않습니다.

```bash
cd /Users/inwoopark/workspace/ai-service/ai-service-project/frangizer/rag
source .venv/bin/activate
python -m app.preflight --env-file ../.env
```

프로세스 환경변수가 `.env`보다 우선합니다(uvicorn과 동일). 통과는 키의 실제 유효성, 계정의 모델 접근 권한, DB 연결, 답변 품질을 보장하지 않습니다. 선택한 `gpt-5.4-mini` 요청 형식은 네트워크 없는 LangChain 검사에도 포함합니다.

로컬 개발 웹은 `frontend/.env.development.local`에 `VITE_USE_MOCK=false`, `VITE_API_BASE_URL=http://localhost:8080/api/v1`을 설정합니다. Docker 프론트도 **빌드 시** `VITE_USE_MOCK=false`를 주입해야 합니다. 생산 빌드의 API 기본 경로는 `/api/v1`입니다. 생성된 프론트 JS에 서버용 API 키나 내부 토큰을 넣지 않습니다.

Docker 구성 도착 후 확인할 연결 조건:

- backend 빌드 context는 저장소 루트, Dockerfile은 `backend/Dockerfile`. Gradle 작업 위치는 `/src/backend`이며 Swagger YAML이 JAR에 포함되어야 합니다. 루트 `.dockerignore`가 실제 `.env`·가상환경·실행 산출물을 제외합니다.
- 컨테이너 간 `DB_URL`, `RAG_URL`은 localhost가 아닌 Compose 서비스 주소를 사용합니다. 로컬 `.env`의 3307은 호스트 연결용이며 DB 컨테이너 내부 포트와 구분합니다.
- backend/RAG가 같은 볼륨을 `/var/lib/frangizer`에 마운트하고 FAISS·상태 DB도 그 아래에 둡니다. 레시피 JSON은 `data/structured/demo_cafe_recipes.json`을 이미지에 COPY하거나 파일로 마운트하고, 경로도 컨테이너 내부 위치로 바꿉니다. 호스트의 절대 경로를 그대로 넘기지 않습니다.
- RAG 명령은 `uvicorn app.bootstrap:create_service --factory --host 0.0.0.0 --port 8001 --workers 1`입니다. 이미지 Python은 검증한 3.11을 사용합니다.
- **첫 색인 전 `/health=503`은 정상**입니다. backend의 시작을 RAG `service_healthy`에 종속시키면 초기 업로드·승인·색인을 시작하지 못합니다. RAG 프로세스 시작과 답변 준비를 구분하고 backend는 초기 색인을 요청할 수 있어야 합니다.

설정이 주입된 RAG 컨테이너 내부에서는 `python -m app.preflight --target docker --service rag`로 검사할 수 있습니다. 이 모드는 RAG에 필요 없는 DB 계정·시연 비밀번호를 요구하지 않습니다. 컨테이너의 같은 볼륨 연결과 실제 네트워크는 Compose/E2E에서 별도로 검증합니다.

## 실제 서비스 실행

루트 `.env.example`을 참고해 **루트 `.env` 한 곳**에 backend/RAG 공통 값을 설정합니다. 실제 비밀값은 Git에 넣지 않습니다. RAG 전용 항목은 `rag/.env.example`에 정리했습니다.

- `JWT_SECRET`: Java와 동일한 UTF-8 문자열, 최소 32바이트. Base64 디코딩하지 않습니다.
- `INTERNAL_TOKEN`, `JWT_ISSUER=frangizer`, `JWT_AUDIENCE=frangizer-api`를 공유합니다. 알고리즘은 HS256으로 고정합니다.
- `LLM_API_KEY`, `LLM_MODEL`, `EMBEDDING_MODEL`을 명시합니다. 임베딩 어댑터는 `text-embedding-3-small` / `text-embedding-3-large`를 지원하며 자동 기본 모델은 없습니다. 별도 `EMBEDDING_API_KEY`도 사용할 수 있습니다.
- `DOCUMENT_STORE_DIR`: Java와 같은 절대 경로. 공유 볼륨은 `/var/lib/frangizer`입니다. 로컬에서는 쓰기 가능한 저장소의 `var/` 절대 경로를 사용할 수 있습니다.
- `FAISS_DIR`: 기본 `/var/lib/frangizer/faiss`. `RAG_STATE_DB`: 질의 결과 재사용용 SQLite 경로.
- `RECIPE_STRUCTURED_FILE`: 선택 사항. 구조화 경로를 켜려면 저장소의 `data/structured/demo_cafe_recipes.json` 절대 경로를 지정합니다.

```bash
cd /Users/inwoopark/workspace/ai-service/ai-service-project/frangizer/rag
source .venv/bin/activate
python -m uvicorn app.bootstrap:create_service --factory \
  --env-file ../.env --host 127.0.0.1 --port 8001 --workers 1
```

Docker에서는 내부 네트워크 접근을 위해 `--host 0.0.0.0`을 사용합니다. Java의 `RAG_URL`은 실행 위치에 맞춰 `http://localhost:8001` 또는 `http://rag:8001`로 설정합니다. 브라우저는 Java API만 호출합니다.

실행 순서는 RAG → Java → 본사 로그인·문서 업로드·승인 → 색인 성공 확인 → 배포 → 점주 질문입니다. 레시피 시연 자료는 manifest의 `document_id=demo-cafe-recipes`로 등록해 구조화 JSON과 연결합니다. 최초 색인 전 health는 503입니다. 설정·유효한 산출물이 준비되면 200이며, health가 외부 제공자의 인증·답변 품질까지 검증하지는 않습니다. 모델 설정이 없으면 질문은 503, 임베딩 설정이 없으면 색인은 `EMBEDDING_NOT_CONFIGURED`로 실패합니다.

## 검색과 색인 경계

### 한국어 Hybrid 검색과 재순위화

- Java가 허용한 브랜드·역할·판본·적용 시점으로 먼저 제한합니다. Dense 검색과 Kiwi 형태소 기반 BM25를 각각 최대30개 검색한 뒤 RRF(k=60)로 결합합니다. `우유`, `이물`, `직원` 같은 짧은 명사와 법조문·버전 식별자를 보존합니다.
- 검색마다 RRF 후보 최대30개를 보존합니다. 비교 질문은 두 검색어의 후보를 RRF로 합친 뒤 최대30개에 재순위화를 한 번만 적용합니다. 재순위화는 후보를 삭제하지 않고 우선순위만 바꾸며, 실제 작성·검수 입력은 최대20조각·12,000자입니다. 본문을 아직 읽지 않은 후보는 제목·조문·쪽·ID 목록으로 전달하고 필요한 후보만 추가 조회합니다. 재순위화 호출·성공한 호출의 토큰도 전체 모델 예산과 usage에 합산합니다. `RERANK_ENABLED=false`로 끌 수 있습니다.
- 재순위화는 요청 안에서 최대3초·자동 재시도 없음입니다. 후속 작성·검수 예산이 부족하면 생략하고, 실패하거나 빈 선택을 반환하면 기존 Hybrid 검색 결과를 유지합니다. 긴 본문은 머리말과 검색어에 맞는 뒤쪽 구간을 함께 발췌해 선택합니다. 이는 순위 판단용이며 답변에는 해시로 검증한 원문을 제공합니다. 문서 본문/비밀값을 로그에 기록하지 않습니다.
- 경량 다국어 Cross-encoder도 비교했으나 해당 한국어 평가에서 근거 순위가 하락해 기본 구성에서는 제외했습니다. LLM 재순위화는 지연·비용이 있으므로 평가 결과와 함께 관리합니다.
- `read_sections`는 후보 본문과 같은 부모의 조각, 원문이 명시한 조항 참조를 한 단계 조회합니다. 같은 부모는 문서·판본·revision·적용 기간이 일치해야 하며, 다른 조항은 원문의 문서명·조 번호로 연결합니다. `법`/`영` 참조는 해당 문서 제목의 법·시행령 관계로 해석합니다. `같은 법/영/규칙`은 앞서 명시된 대상의 종류가 일치할 때만 연결하고, 새 문단이나 불명확한 외부 법명 뒤에는 앞선 대상을 재사용하지 않습니다. 대상이 명시되지 않은 위임 내용을 추측하거나 참조를 재귀 확장하지 않습니다. 허용 판본·권한·시점·해시를 다시 검사하고 미검수 형제/참조 표는 제외합니다. 요청한 조각을 요청 순서대로 먼저 담은 뒤 연결 문맥을 추가하며, 처음 요청한 조각부터 최대20조각·12,000자 제한을 적용합니다. 크기 때문에 담지 못한 조각 ID와 참조 누락은 모델에 알리고, 생략한 요청 조각에서 문맥을 더 확장하지 않습니다.
- 기존 색인은 권한·판본·시점 필터 뒤에 원문 제목의 구간별 계층을 복원합니다. 기존 벡터를 다시 만들지 않고 BM25·재순위화·생성 문맥에 반영합니다. 새 색인(`chunker-v6-context`)은 `text`를 인용 원문으로 유지하고 `hierarchy`·`search_text`·`search_sha256`를 별도로 저장하여 문맥 포함 텍스트를 임베딩합니다. 기존 벡터에도 새 문맥을 임베딩하려면 별도 새 revision 색인·배포가 필요합니다.
- 새 검색 단계는 기존 색인 산출물을 그대로 읽으므로 실행 자체에는 재색인이 필요 없습니다. 실패 질문을 정답 문장으로 하드코딩하지 않습니다. 검색 소요 시간과 비용표 조회·교정·검수의 분기 및 선택 ID를 문서 본문·비밀값 없이 기록하고, 응답에 전체 지연 시간을 포함합니다.
- 형태소 분석기와 기존 색인의 토큰 캐시는 서버 시작 시 준비합니다. 초기 기동은 수 초 늘어날 수 있으나 첫 질문에 초기화 비용을 전가하지 않습니다. 부록의 명시적 번호·업종 제목은 원문 오프셋별로 연결합니다. 줄바꿈된 괄호의 한정 조건도 보존하며, 누락 쪽·미검수 표를 넘어 제목을 상속하지 않습니다. 이는 구조적인 제목 복원이며 법적 업종 분류나 전체 의미 청킹이 완료된 것은 아닙니다.

### 표 추출·검수와 근거 없는 답변

- 본문은 PyMuPDF로 읽고, A가 원본 PDF에 연결해 만든 `data/structured/table_transcriptions.json`의 표 기록을 우선 적용합니다. 해당 쪽은 Camelot/pdfplumber로 다시 추출하지 않습니다. 기록이 없는 새 표만 영역을 제한한 로컬 추출 후보로 처리합니다. 기존 소비자분쟁 표의 좌표 기반 짝짓기와 구조화 레시피 경로는 유지합니다.
- 검수 표는 `table.schema=reviewed-cells-v1`과 함께 `columns`, `rows`, `unit`을 산출물에 보존합니다. 조회 후 `generation/table_evidence.py`가 제목·단위·완전한 행을 실제 인용 원문과 대조합니다. 메타데이터만 존재하거나 미검수·부분 행이면 선택지로 쓰지 않습니다. 이전 형식은 기존 텍스트 경로로 처리합니다.
- 새 표 형식은 색인 revision 계산에 포함됩니다. 서버 재시작만으로 이전 색인에 행·열이 생기지는 않습니다. 새 revision으로 재색인한 뒤 Java가 해당 revision을 허용해야 활성화됩니다. 개발 환경에서는 아래 일회성 스크립트로 기존 문서의 revision을 갱신할 수 있습니다. 기존 배포 산출물은 유지합니다.
- 일반 쪽 분할에서 표 밖 설명은 별도 조각으로 저장하고 표 때문에 같은 쪽의 설명까지 차단하지 않습니다. 조 단위 법령은 기존 보수적인 쪽 경고를 유지합니다. 표 조각에는 열 이름·행 값과 주변 설명(단위·각주)을 함께 넣습니다. 경계를 분리하지 못하면 기존 경고를 유지합니다.
- A의 표 기록은 PDF 해시와 원문 값·단위·제목 대조를 통과하면 `table_reviewed`로 색인하고 답변 근거로 사용합니다. 로컬 추출 후보는 검수 전까지 `table_needs_review`를 유지합니다. 생성 모델에는 미검수 조각의 본문을 보내지 않고 문서명·쪽·검수 표시만 보냅니다. 미검수 표를 인용하면 상태에 관계없이 원문 확인 안내로 교체하고 출처 카드에도 미검수 표시를 합니다.
- 출처가 0개인 초안은 `answered`여도 502로 처리하지 않고 `needs_review`와 고정 안내로 바꿉니다. 모델이 만든 상식·처리 순서는 제거합니다. 별도 근거 평가에서 선택한 확인 질문은 최종 검수를 통과한 경우에만 유지하고, 담당자 최종 판단 안내는 고정 문구로 유지합니다. 작성 모델의 잘못된 출처 ID는 제한된 재작성/항목 보류로 처리하며, 검색 결과의 권한 위반·내용 해시 불일치·실제 제공자 장애는 계속 오류입니다.
- 질문을 최대6개 확인 항목으로 나누고 각 항목에 상태(`supported`, `missing_evidence`, `missing_user_context`, `conflict`), 원문 구간 참조와 적용 조건을 연결합니다. 상태·출처의 ID 유효성은 서버가 검사하지만 의미적 적용 판단은 여전히 모델에 의존합니다.
- 단순 조회(`question_plan.intent=lookup`)이고 모든 승인 항목에 검수 표 선택지가 있으면 생성 모델은 `table_choice_ids`만 고릅니다. 자유 작성 blocks는 출력 스키마에서 금지합니다. 선택지는 질문 항목·행·열·값·단위·출처를 서버가 고정하고, 서버가 원문 값과 인용을 복원한 뒤 기존 수치 검사·의미 검수를 거칩니다. 해석·비교·포함 관계 상담과 표로 다루지 못하는 혼합 질문은 기존 설명 블록 경로를 사용합니다. 별도 모델 호출이나 외부 도구는 추가하지 않습니다. 서버가 미확인 항목 안내·응답 상태를 조립합니다. 문장부호로 답변을 다시 나누지 않으며 단계·인용문도 고정된 블록 ID로 검수합니다. 같은 질문 항목의 설명과 단계는 함께 통과하거나 함께 보류하며, 통과한 항목만 부분 답변(`needs_review`)으로 유지하고 문서 누락을 사용자 조건 질문으로 돌리지 않습니다.
- 검수 표의 행·열 이름이 복원 질문에 명시된 단순 조회는 해당 표를 코드로 선택지에 연결하고 재순위화·근거 평가 호출을 생략합니다. 이 경우에도 모델의 필드 선택과 마지막 질문 적합성·조건 검수는 필요합니다. 같은 행에서 선택한 금액·기한은 한 사실 블록으로 묶어 단위·조건을 함께 표시합니다. 명칭이 맞지 않거나 구조화 근거가 없으면 기존 상담 흐름을 사용합니다.
- 항목·값·단위·원문 구간을 묶어 숫자를 검사합니다. 명시적 구분자가 있는 행은 항목과 값의 뒤바뀜도 거부하며, 페이지·판본·요청 날짜의 숫자는 사실 수치의 근거로 인정하지 않습니다. 모호한 산문·복잡한 표 관계는 의미 검수가 필요하므로 모든 표를 결정적으로 검증한다는 뜻은 아닙니다. 부분 답변에도 같은 수치 검사를 적용합니다.
- `counsel_decision`에는 오류 코드·블록 ID·질문 항목 상태·근거 구간 ID·잔여 시간·호출 수·단계별 누적 시간이 기록됩니다. 질문·초안·원문·모델의 자유 서술 사유는 남기지 않습니다.
- 검수 파일 `data/structured/table_reviews.json`은 source SHA·표 SHA·검수자·검수 시각을 기록합니다. PDF나 표 추출 결과가 바뀌면 기존 승인을 재사용하지 않습니다. Docker에서는 구조화 자료와 함께 읽기 전용으로 연결합니다.

표 후보 내보내기와 원문 대조 후 승인(저장소 루트에서 실행):

**기존 배포 자료는 재시작만으로 바뀌지 않습니다.** 분할·산출물 형식과 검수 기록은 새 색인 revision을 만듭니다. Java가 그 revision을 허용 판본으로 지정해야 검색에 반영됩니다. 새 문서는 기존 등록 → 승인 → 색인 → 배포 흐름을 사용합니다.

개발 중 이미 배포한 검수 표 문서 한 건은 시드·업로드 없이 아래처럼 재색인합니다. 실행 중인 Docker Compose의 DB·RAG를 사용하며 Python 외 별도 패키지는 필요 없습니다.

```bash
# 대상 조회만
python3 rag/scripts/dev_reindex.py --document-id paik-franchise-disclosure
# 새 job으로 색인 → 원본·산출물·표 행 검증 → 해당 판본의 revision 갱신
python3 rag/scripts/dev_reindex.py --document-id paik-franchise-disclosure --apply
```

백엔드 코드·API·DB 스키마를 바꾸지 않는 개발용 처리입니다. 기존 판본의 승인·배포·적용일·파일과 다른 문서는 유지합니다. `rag/.demo/dev-reindex-*/`에 이전 설정, 요청, 작업 결과와 복구 SQL을 저장합니다. 색인·검증 실패 시 DB를 갱신하지 않으며, 다른 작업이 revision을 먼저 바꿨을 때도 중단합니다. 이미 같은 revision이면 DB 변경을 생략합니다. 확인은 기존 답변 재시도 대신 새 대화의 새 질문으로 합니다.

### 이번 변경 배포 시 팀 공유 사항

- 기존 색인도 읽을 수 있지만, `chunker-v6-context`의 상위 문맥 임베딩과 `reviewed-cells-v1` 표 필드를 모두 적용하려면 기존 문서를 새 revision으로 재색인합니다. 정보공개서부터 적용하고 나머지 문서도 순차 갱신합니다. 마지막 프롬프트·검수 정리만을 위한 재임베딩은 아닙니다.
- RAG 이미지를 먼저 다시 빌드합니다. 새 의존성인 `kiwipiepy`도 포함되어야 합니다. 임베딩 모델·차원을 바꿀 필요는 없으며 재색인은 실제 임베딩 API 비용이 발생합니다.
- 원본 삭제·재업로드·시드 재실행은 필요 없습니다. 기존 시드는 등록된 자료를 건너뛰므로 재색인 대용으로 쓰지 않습니다. 위 스크립트는 로컬 시연용으로 DB의 허용 revision도 갱신합니다. 운영 환경에는 별도의 승인된 revision 전환 절차가 필요합니다.
- Java의 `allowed_versions.index_revision`이 새 revision을 가리켜야 검색에 반영됩니다. 이미 배포한 판본을 화면에서 다시 승인하는 절차와는 다릅니다. 공개 API·JWT·응답 형식은 유지합니다.
- A의 원본·검수 자료는 그대로 사용합니다. D는 새 대화에서 출처·확인 질문·보류 표시를 확인하고, E는 공유 저장소와 재빌드 후 준비 상태를 확인합니다. 복잡한 법령 참조·예외 조건 누락·불필요한 출처는 남은 한계입니다.

이미 저장된 대화·같은 attempt_id의 재사용 결과는 재생성하지 않습니다. 화면 확인은 새 대화에서 진행합니다.

- 저장 키는 `DOCUMENT_STORE_DIR` 아래 `documents/...`만 허용하고 경로 이탈·심볼릭 링크 이탈·원본 SHA256 불일치를 차단합니다.
- A의 PDF/TXT/MD 추출·분할을 사용합니다. FAISS, chunks.jsonl, build-manifest, quality-report를 한 revision으로 원자적으로 저장합니다. 같은 입력·설정은 재사용하고 모델·차원 변경은 새 revision을 만듭니다.
- 서비스는 **단일 worker**, 색인 동시 실행 1개·대기 포함 최대 16개입니다. 같은 작업 ID와 다른 내용은409, 과부하는503입니다. 재시작 시 남은 queued/running은 failed + `INTERRUPTED`가 됩니다. 새 job_id로 다시 요청해야 합니다.
- 검색은 Java가 전달한 `(document_id, version_id, index_revision)`에만 접근합니다. 브랜드·역할·조각 적용 기간을 **유사도 순위 계산 전에** 제한합니다. 허용 범위를 자동으로 넓히지 않습니다.
- 모델·차원·정규화 방식·본문 해시·조각 매핑을 검사합니다. pickle을 읽지 않습니다. 주요 검색 결과와 필요한 문맥은 최대20조각·12,000자로 제한합니다. 본문 밖의 후보 목록도 같은 권한·해시 검사를 통과해야 하며, 원문 조회는 후보의 부모 또는 명시된 참조 조항으로 제한합니다.
- `legal_temporal_reviewed=false`는 색인 내부 검수 정보로 유지하며 답변 앞에 검수 표시를 붙이지 않습니다. 이 표시를 생략해도 시행일 검수가 완료된 것으로 처리하지 않습니다. 표의 `table_needs_review` 또는 `table_pairing_mismatch` 경고가 있는 출처로는 수치를 확정 답변하지 않고 `needs_review`로 반환합니다. OCR·법률적 정확성 평가는 별도로 필요합니다.

## 레시피의 생성 없는 응답

구조화 파일을 설정하면 명확한 단일 메뉴·기본 1잔의 계량·제조 순서를 저장된 값으로 반환합니다. 양·단위 환산을 하지 않습니다. 미지원 질문은 상담 에이전트가 처리합니다.

구조화 JSON 자체를 배포 증거로 쓰지 않습니다. **Java의 허용 판본 + 브랜드/역할/시점 + 색인 원본 SHA256 + 쪽 번호 + 본문의 재료량·순서 대조**를 통과한 경우에만 사용합니다. 메뉴·판본 헤더와 HOT/ICED의 재료표·순서를 해당 원문 구간에서 대조합니다. 옵션·펌프는 현재 판본의 확인사항 원문에 명시된 경우만 사용하며, 모르는 형식은 빠른 경로로 확정하지 않습니다.

예: `아이스 바닐라라떼 시럽 얼마 넣어?`는 정확한 값·출처를 반환합니다. 온도 미지정이어도 요청한 재료량이 HOT/ICED에서 같으면 공통 값을 바로 반환합니다. 양이 다르면 온도를 확인하고, `아이스 딸기라떼 다음 단계?`는 완료 단계를 확인합니다. `1단계 완료, 다음 단계?`는 저장된 2단계를 반환합니다. 저장된 옵션과 전용 펌프 횟수는 그대로 조회하지만, 여러 잔·용량 변경·미등록 옵션·임의 펌프 환산은 빠른 경로로 강제 처리하지 않습니다. 대화의 예전 답변을 완료 단계로 간주하지 않습니다.

응답 계약은 동일하며 이 경로는 `retrieval.llm_called=false`, 모델/임베딩 토큰 0입니다. 문맥에서 생략된 메뉴를 복원하는 질문은 현재 일반 상담 경로를 이용합니다.

## 상담·재시도

기본 그래프는 필요한 질문 대상 복원 → Hybrid 검색·선택적 재순위화 → 항목과 초안 작성 → 독립 검수 → 응답 조립입니다. 작성 전 별도 LLM 근거 승인 단계는 없습니다. 재순위화와 질문 복원이 없는 명시적 질문은 작성·검수 2회가 기본입니다.

- 작성자는 `ProposedAnswer`에 질문 항목(`DraftItem`)·사실 블록·미확인 범위·확인 질문을 함께 제안합니다. `disposition=answer`도 출판 승인이 아닙니다. 일반 초안의 인용은 서버가 부여한 원문 구간 번호를 선택하고, 서버가 실제 ID로 복원합니다. 서버는 항목·구간 ID, 실제 인용 원문, 수치·단위·행 연결을 검사하고 최종 의미 검수를 거칩니다.
- 일반 초안은 문장별 인용만 선택합니다. `DraftItem`에는 중복 출처 필드가 없으며 항목별 출처는 서버가 해당 항목의 문장들에서 중복 없이 모읍니다. 레시피 도구 호출만 `lookup.source_refs`로 조회에 사용할 원문을 선택합니다. 표 셀은 복원된 문장의 출처를 사용합니다. 이 조립은 근거의 의미적 적합성을 승인하지 않습니다.
- 문서에 명시된 대상·조건·예외 설명(`document_rule`)과 실제 사용자 상황의 적용 판단(`case_application`)을 구분합니다. 적용이 불명확해도 독립적으로 유용한 문서 기준은 설명할 수 있지만, 참조 내용이나 미확인 대상의 의무·허용을 추정하지 않습니다.
- 명시적 표 조회는 기존 셀 번호 선택을 유지합니다. 일반 초안에도 검수된 표 셀 선택지를 제공하여 값·단위·출처를 서버가 복원합니다. 선택한 표 항목을 자유 문장으로 중복 작성할 수 없습니다. 레시피 조회 인자도 공통 조회 실행기로 연결합니다.
- 검수는 작성자가 인용한 구간뿐 아니라 현재 확보한 사용 가능한 본문도 확인합니다. 답할 근거가 있는데 미확인으로 남겼는지도 검사하며, 아직 읽지 않은 후보는 제목·쪽·ID 목록으로만 전달합니다. 후보 목록은 사실 근거가 아닙니다.
- 모델의 검수 출력은 문장별 `verdict`·이유·인용 번호와 질문 항목의 완료 여부로 제한합니다. 서로 중복되는 긍정 플래그·조건 누락 설명을 모델에 동시에 요구하지 않으며, 서버가 단일 판정에서 내부 오류 코드를 계산합니다. 이 형식 자체가 의미적 정확성을 보장하지는 않습니다.
- 근거 부족은 검수의 요청에 따라 `search_documents` 또는 `read_sections`, 설명 오류는 해당 항목 재작성, 검수 참조/출력 오류는 초안을 유지한 검수 보완으로 처리합니다. 모델 출력의 잘못된 구간·수치 연결은 의미 검수 전에 재작성할 수 있지만 새로운 검색을 유발하지 않습니다.
- 재작성에는 실패 코드, 검수의 구체적 이유, 실패 문장·수치 연결·인용 ID를 전달합니다. 검수 이유는 새 근거가 아니며 현재 원문과 다시 대조합니다. 전체 원문을 보완 입력에 중복 복사하지 않습니다.
- 수치 검사는 `100분의 20`과 `20%`처럼 값이 같은 백분율 표기를 동등하게 인식합니다. 원문·출처는 변경하지 않으며 다른 값·화폐 단위·잘못된 인용 구간은 계속 거절합니다. 임의 산술이나 물리량 환산은 하지 않습니다.
- 수치 연결 정보가 빠졌거나 구간 번호가 잘못됐을 때, 이미 인용한 구간에 같은 값·단위가 명시적으로 유일하게 확인되는 경우에만 연결 정보를 보완합니다. 새 출처·수치·단위를 만들지 않습니다. 모호한 후보·다른 행의 금액·값이나 단위 오류는 기존 검사에서 계속 거절합니다.
- 모든 보완은 공통 1회 예산을 공유합니다. 전체 모델 호출 기본 최대6회, 도구 호출 최대3회, 검색 최대3회 및 Java가 보낸 전체 시간 제한을 유지합니다. 남은 시간이 부족하면 추가 작업을 하지 않습니다. 시간 초과 시 검수된 부분 답변이 있으면 미확인 상태로 반환하고, 없으면 `504 UPSTREAM_TIMEOUT`, `retryable=true`를 유지합니다.
- 같은 원문으로 재작성할 때 검수 통과한 독립 항목은 재생성하지 않습니다. 전체 문맥의 최종 검수는 다시 수행하고, 새 검수가 거절한 내용을 옛 답으로 되살리지 않습니다. 재검색으로 근거가 바뀌면 이전 검수 스냅샷은 폐기합니다.
- 합계·비교처럼 의존적인 내용은 하나의 항목으로 검수하고, 일부 문장을 지워 의미가 바뀌는 부분 답변은 만들지 않습니다. 원문 합계 행과 구성 항목을 함께 제시한 경우 별도 산술이나 자연어 재서술을 강제하지 않습니다. 해당없음·면제·미기재는 구분합니다.
- 중복 제거는 검수 후 동일 항목·문서 판본·적용 기간·문장·수치에만 적용하고 승인된 출처를 보존합니다. 값이 같다는 이유만으로 다른 조건·문서·판본을 합치지 않습니다.
- 권한·브랜드·판본·시점·해시·미검수 표 경계는 모델 판단과 무관하게 유지합니다. 이전 AI 답변은 대상 복원 문맥일 뿐 사실 근거가 아닙니다. 답변 없이 확인 질문만 반환하는 경우에도 검수를 통과해야 합니다.

### 내부 계약과 출처

각 모듈은 아래 책임을 유지합니다. 파일 수를 줄이기 위해 검색·검수·원문 조립을 한 파일로 합치지 않습니다.

| 모듈 | 책임 |
|---|---|
| `generation/question.py` | 질문 대상 복원과 검색 계획 |
| `generation/agent.py` | 실행 순서, 호출·시간 예산, 한 번의 보완 경로 |
| `generation/model.py` | 모델 계약, 초안의 미검수 항목 상태 계산, 공통 모델 호출·응답 검사 |
| `generation/table_evidence.py` | 일반 설명·표 필드 선택 스키마와 셀·단위·출처 복원 |
| `generation/review.py` / `evidence_policy.py` | 검수 계약, 인용·수치·표 품질 검사 |
| `generation/answer.py` | 검수 결과 보존, 최종 답변·출처 조립 |

초안의 항목 상태는 `ProposedAnswer.to_assessment()`에서 한 번 계산합니다. 모델 호출·파싱은 `LangChainModel._structured()`로 통일하고, 표 선택 스키마·셀 복원·합계 확장은 `table_evidence.py`에 모았습니다. 검수 판정 어휘와 내부 플래그 변환은 `review.py`가 관리합니다. 테스트의 공용 원문·블록·드라이버·준비 코드는 `tests/support.py`를 사용합니다.
- 상담은 원문에 연결한 직접 답변을 작성하고 기존 검수를 거칩니다. 검수의 `question`은 작성자가 만든 `items.requirement`로 덮어쓰지 않습니다. 사용하지 않는 규정 카드 엔진·JSON·전용 계약과 이전 비교 목록 검수는 제거했습니다. 법령·정보공개서 원본과 검색 색인은 그대로 유지합니다.
- `chunk_id + unit_id`는 실제 원문 오프셋으로 만듭니다. 검수 모델은 서버가 고정한 블록·항목 키와 각 블록의 인용 선택 번호만 사용합니다. 검수 누락·잘못된 대상 확대·조건 누락은 긍정 플래그만으로 통과하지 않습니다.
- 최종 출처는 검수한 모든 자료가 아니라 실제 답변에서 사용한 구간입니다. `sources[].excerpt`는 1500자 계약을 지키며 필요한 경우 일부 발췌임을 명시합니다. URL·판본·쪽의 공개 계약은 바꾸지 않습니다.
- LLM 작성·검수는 의미적 정확성을 보장하지 않습니다. 운영 질문의 실질 답변·출처·보류 여부를 함께 평가해야 하며, HTTP 200이나 자동 테스트 통과만으로 실제 상담 정확도를 판단하지 않습니다.
