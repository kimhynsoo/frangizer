# 프랜자이저 프론트엔드

Vue 3 + Vite + Pinia 기반 프론트엔드 초안. 서비스명은 프랜자이저(frangizer)다.
공개 API 기준: `../docs/api/API_명세서.md`와 `../docs/api/public.openapi.yaml`.

## 실행

Node.js 22.12 이상 또는 24 이상과 npm이 필요하다. 저장소 루트가 아닌 `frontend/`에서 실행한다.

```sh
npm ci
npm run dev
```

브라우저: http://127.0.0.1:5173

PC와 모바일은 같은 `frontend/` 프로젝트를 사용한다. 휴대폰 너비(620px 이하)에서는
하단 메뉴·카드형 목록·작은 질문 입력창을, PC에서는 사이드바·표·넓은 대화를 표시한다.

기본은 **실제 API 모드**다. 루트에서 Docker 서비스를 실행하면 개발 서버가 `/api`를
로컬 80 포트로 전달한다. 테스트 계정은 `demo-owner-a001`, `demo-prospect-01`, `demo-hq-01`이며,
비밀번호는 해당 API 환경의 설정을 사용한다. 실제 `.env`와 비밀값은 커밋하지 않는다.
합성 데이터만 확인하려면 `.env.local`에 `VITE_USE_MOCK=true`를 설정하고 개발 서버를 재시작한다.
이때 계정은 `demo-owner-a001`, `demo-prospect`, `demo-hq`, 합성 시연 비밀번호는 `demo-password`다.

같은 Wi-Fi의 휴대폰에서는 `http://<PC의 내부 IP>:5173` 또는 Docker의
`http://<PC의 내부 IP>`로 접속한다. 마이크 입력은 HTTPS 또는 localhost와 권한이 필요하다.
이전 모바일 복제 폴더 및 5174 포트는 사용하지 않는다.

## 팀원끼리 같은 화면으로 확인하기

최신 프론트 변경이 병합된 `main`과 같은 로그인 역할을 사용한다. `git fetch`만으로는 실행 중인 파일이 갱신되지 않는다.

### 로컬 개발 서버

```sh
git switch main
git pull --ff-only origin main
cd frontend
npm ci
npm run dev
```

기존 개발 서버는 종료하고 다시 실행한다. 브라우저 주소는 터미널에 표시된 현재 서버 주소를 사용한다.

### 이미 실행 중인 Docker 웹

저장소 루트에서 최신 `main`을 받은 뒤 웹 이미지를 다시 빌드한다. 실행 중인 컨테이너에 `git pull`만 해서는 새 화면이 반영되지 않는다.

```sh
git switch main
git pull --ff-only origin main
docker compose build web
docker compose up -d --no-deps web
```

이 명령은 DB·백엔드·RAG가 이미 실행 중인 환경의 웹 갱신용이다. 최초 전체 실행은 루트 README를 따른다.

### 프론트 수정 중 자동 반영 (실제 API 모드)

Docker Desktop을 켜고 저장소 루트에서 실행한다. Docker Compose 2.22 이상이 필요하다.

```sh
docker compose up -d --build
docker compose watch --no-up --prune=false web
```

Watch 터미널을 켜둔 채 `http://localhost`(WEB_PORT를 바꿨으면 해당 포트)에서 확인한다.
`frontend/` 또는 `nginx/` 파일을 저장하거나 `git pull`로 갱신하면 웹 이미지가 자동으로
재빌드·재시작된다. 빌드 완료 후 브라우저를 새로고침한다. API·DB·RAG는 같은 Compose
서비스에 연결되며 샘플 모드로 전환하지 않는다. Watch 종료는 해당 터미널에서 Ctrl+C이며
서비스는 계속 실행된다. 테스트·빌드 산출물·환경 파일은 감시에서 제외한다.

팀원은 PR 병합 후 최신 main을 받거나, 병합 전 검토할 PR 브랜치를 받은 뒤 위 명령을 실행한다.
PR 생성만으로 팀원 PC의 코드는 갱신되지 않는다. 이미 Watch 중이면 프론트 변경은 pull 후
자동 재빌드되지만, 백엔드·RAG·Compose 설정도 변경됐으면 전체 `up -d --build`를 다시 실행한다.
`.env`와 DB·문서 색인 데이터는 PC별로 별도 준비한다.

### 모드·계정 확인

- `npm run dev`와 Docker 웹의 기본은 모두 실제 API 모드다. UI 코드가 같아도 문서·공지·답변 데이터는 다를 수 있다.
- 샘플 모드를 함께 확인하려면 `frontend/.env.local`의 `VITE_USE_MOCK=true`를 사용하고 개발 서버를 다시 시작한다. 실제 연동을 확인할 때는 아래 실제 서버 연결 설정을 따른다.
- 샘플 계정: `demo-prospect`, `demo-owner-a001`, `demo-hq`. 실제 API의 시드 계정: `demo-prospect-01`, `demo-owner-a001`, `demo-hq-01`이며 비밀번호는 서버 담당자가 설정한 `DEMO_PASSWORD` 값이다.
- 비교할 때 같은 역할·브랜드·점포로 로그인한다. FAQ는 예비 점주 전용, 읽기 기능·미확인 숫자는 역할에 따라 다르게 표시된다.
- 변경 후에도 이전 화면이면 실행 중인 서버 폴더·브랜치·접속 주소를 확인하고 브라우저를 강력 새로고침한다.

## 실제 서버 연결

`frontend/.env.local`을 만들고 다음 값을 설정한 뒤 개발 서버를 재시작한다.
실제 환경 파일은 커밋하지 않는다. `.env.example`에는 변수 이름만 보관한다.

```dotenv
VITE_USE_MOCK=false
VITE_API_BASE_URL=/api/v1
```

배포 시 `VITE_API_BASE_URL=/api/v1`을 사용하고 Nginx가 Java 서버로 전달하도록 한다.
기본 개발 설정은 같은 출처의 `/api` 프록시를 사용한다. 외부 Java 서버를 직접 지정하는 경우에만 해당 서버의 CORS 허용 출처에 프론트 주소가 필요하다. `Authorization`, `Idempotency-Key`, `Content-Type` 요청 헤더와
`X-Request-ID`, `Retry-After` 응답 헤더 처리도 백엔드 담당자와 확인한다.
모델 API 키와 JWT 서명키는 프론트 환경변수에 넣지 않는다.
실제 서버 장애 시 샘플 데이터로 자동 대체하지 않는다.

## 구현 범위

- 역할별 로그인, `/me` 권한 기반 메뉴·라우트, 토큰 만료 시 재로그인.
- 질문·답변·출처·판본·기준 시점, 확인 필요·담당자 검토 상태, 대화 복원, 도움 여부 피드백.
- 문서 목록·판본 이력·본문 조각·인증된 다운로드, 등록·승인·2초 간격 색인 상태 조회·배포.
- 공지와 점주 확인, 본사 전체 대상 확인율과 필터·페이지별 점포 목록.
- 본사 기간·지역·점포·분류·주제 필터, 문의 집계·상세·처리 상태 수정 및 동시 수정 충돌 안내.
- 모바일 메뉴, 반응형 레이아웃, 키보드 포커스와 접근성 라벨.

화면에서 HTTP를 직접 호출하지 않는다. `src/api/`의 모듈을 통해 공통 클라이언트를 사용한다.
로그인만 `data` 래퍼가 없으며 나머지 응답은 명세의 래퍼를 유지한다.
질문·문서 등록·승인·배포의 재시도에는 같은 `Idempotency-Key`를 쓴다.

## 시연의 한계

`src/demo/mock.js`는 브라우저 안의 합성 데이터로 흐름을 흉내 낸다. 실제 RAG·JWT 인증·DB·문서 추출·보안 검증 서버가 아니다.
레시피 시연은 `data/manifest.json`과 실제 합성 PDF를 대조한 `src/demo/synthetic-materials.json` 스냅샷을 이용한다. 기본 바닐라라테 HOT·ICED와 배포 후 허니자몽블랙티 ICED만 지원하며, 다른 질문·주문 옵션은 실제 RAG 연결 전까지 추가 확인으로 안내한다. upstream API 계약 예시는 변경하지 않는다.
통합 시연의 승인·배포·확인 상태는 같은 브라우저 실행 중에만 유지되며 새로고침하면 초기화된다.
초기 레시피 다운로드는 **합성 안내 TXT 발췌**다. 저장소에 실제 PDF가 있어도 프론트 정적 자산으로 자동 공개하지 않는다. 실제 서버의 원본 다운로드 연결은 별도 검증 대상이다.
직접 업로드한 파일은 시연 실행 중 해당 파일을 내려받는다.
샘플 계정·토큰은 실제 서버에서 사용할 수 없다.

### 새 자료에 맞춘 레시피 시연

- 초기 시연에만 v1.0을 명시적으로 배포 상태로 설정한다. `source`/`staged` 폴더 위치에서 승인·배포 상태를 추론하지 않는다.
- v1.0: `카페 표준 레시피 북 (합성)`, 파일 8쪽, 적용 시작 2026-10-01. 바닐라라테는 파일 5쪽 / 인쇄 6쪽이다.
- v1.1: 파일 10쪽, 바닐라라테는 파일 5쪽 / 인쇄 5쪽, 신메뉴는 파일 9쪽 / 인쇄 10쪽이다. 초기 문서 목록에 넣지 않는다.
- 본사 문서 등록에서 **레시피 v1.1 등록 예시 채우기** → `data/staged/합성_카페_레시피_v1.1.pdf` 직접 선택 → 초안 등록 → 검수·승인 → 검색 준비 → 배포한다.
- v1.1은 승인·배포 전에는 답변에 사용하지 않는다. 배포 후에도 기준 시점이 2026-10-26 00:00 KST 이후일 때만 선택한다.
- 바닐라 시럽은 20 mL/4펌프에서 15 mL/3펌프로 바뀐다. 우유·샷·얼음량은 바뀌지 않는다.
- 선택한 업로드 파일의 SHA-256과 문서 ID·판본·적용일이 검토된 자료와 일치할 때만 검토된 본문을 연결한다. 다른 파일에서 레시피를 추정하지 않는다.
- v1.0의 `2026-10-25` 종료 표기는 시연에서 25일을 포함하는 것으로 읽어 `2026-10-26T00:00:00+09:00` 미포함으로 명시한다. 날짜·시각 혼용과 `effective_to` → `effective_until`의 일반 변환 규칙은 백엔드·데이터 담당자와 협의할 항목이다.
- 합성 가맹계약서는 저장소에 있지만 적용일이 비어 있다. 임의 날짜나 승인 상태를 만들어 API 시연에 넣지 않으며, 현재 시연의 검색 실패를 저장소 전체에 계약서가 없다는 뜻으로 안내하지 않는다.

## 피크 타임 음성 질문

- 채팅 입력창의 **마이크** 버튼으로 시작한다. 타이핑과 음성 인식 결과는 하나의 입력창·전송 버튼을 공유한다. 마이크 권한은 이 동작에서만 요청한다.
- 메뉴명과 질문을 말하면 말이 끝났을 때 인식을 마친다. 최대 60초·10MB이며 WebM 우선, 미지원 기기에서는 AudioWorklet로 WAV를 녹음한다.
- **말로 확인하기**를 켜면 인식 내용을 기기의 한국어 음성으로 읽어주고, 이어서 확인 명령을 듣는다. “보내기”는 확인 후 전송, “다시”는 새 녹음, “취소”는 종료다. 임의의 문장·침묵·불명확한 명령은 전송하지 않는다.
- 확인을 끄면 같은 입력창에서 문장을 수정하고 전송 버튼을 누른다. 음성 인식 중간 결과도 이 입력창에 표시하며 기존 입력 내용 뒤에 이어 붙인다.
- 타이핑과 음성 모두 같은 기준 시점을 사용한다. 비워두면 현재 기준이며, 설정한 과거·미래 기준 시점도 두 입력 방식에 동일하게 적용한다.
- **답변 읽어주기**는 질문에 대한 답변·제조 순서를 그대로 읽는다. 현재 탭에서 기기에 설치된 한국어 음성이 있을 때 동작하며, 새 녹음·취소·화면 이탈 시 중단한다. 읽기 중지 버튼도 제공한다.
- 음성은 메모리에서만 처리하고 파일·localStorage·sessionStorage에 저장하지 않는다. 취소·다른 화면 이동·탭 숨김 시 마이크 트랙과 오디오 자원을 정리한다.

### STT 서버 모드

`VITE_USE_MOCK=false`에서 녹음한 음성을 `POST /api/v1/stt`의 `audio` 파트로 보내고 `data.text`를 받는다. 인식 완료 자체로 `/rag-query`를 호출하지 않는다. 별도의 음성 또는 버튼 확인 이후에만 질문을 보낸다. 백엔드의 실제 STT 서버 구현과 매장 소음에서의 인식 정확도는 별도 통합 검증이 필요하다.

### 브라우저 음성 체험

실제 STT 서버가 없을 때 사용자가 **브라우저 음성 체험**을 선택할 수 있다. Web Speech `SpeechRecognition` 지원 브라우저에서 실제 음성을 인식하며, 브라우저 제공 서비스가 네트워크를 사용할 수 있다는 안내를 표시한다. 서비스의 WebM/WAV 업로드 API와는 별도 경로이며, 실패 시 가짜 문장을 반환하거나 자동으로 다른 서비스에 보내지 않는다. 미지원 브라우저에서는 제한을 알린다.

**녹음 없이 사용 흐름 보기**는 고정된 예시 문장이라는 표시가 있는 별도 UI 시연이다. 마이크를 켜거나 실제 음성을 인식한 것처럼 표시하지 않는다.

구현 근거: [SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [MediaRecorder 형식 검사](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static), [AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet).

## 내용·업무 흐름 보완

- 현재 판본은 `/documents?as_of=현재시각`의 서버 선택 결과로 판정한다. 배포 상태와 현재 적용·적용 예정 상태를 구분한다.
- 승인 전 네 가지 검수 항목과 검수 메모, 배포 전 공지 제목·변경 요약·적용일·열람 대상을 확인한다. 재시도에는 동일한 메모·제목·멱등키를 유지한다.
- 대화 복원에서 처리 중·시스템 오류 질문을 숨기지 않는다. 상태 새로고침과 질문 재입력을 제공한다.
- 본사 문의 상세에서도 근거·출처·검토 사유·추가 질문을 확인하고 원문으로 이동할 수 있다. 분류 상태도 표시한다.
- 집계에 시스템 오류·처리 중·분류 대기 건수를 표시하고 지표 분모를 설명한다. 공지 확인 현황은 지역별로 필터링한다.
- 원천 URL이 있으면 HTTP(S) 공식 원문 링크를 제공한다.

`handoff` 문의 요약은 현재 응답의 질문·답변·검토 사유·추가 확인 항목을 합쳐 구성한다.
전용 필드 도입 여부와 `public_disclosure`/노션의 가공 참고서 자료 유형 차이는 팀 확인이 필요하다.
실제 서버·시연 계정으로 수행하는 전체 통합 검증은 아직 하지 않았다. 브라우저 검증에서는 사용자의 실제 마이크를 켜지 않았으며, 음성 장치·인식 이벤트·침묵·취소·권한 실패는 대체 장치/이벤트로 자동 검증한다.

## 호출어로 질문하기

질문 화면에서 **음성 대기 켜기**를 누른 뒤 “시리”라고 부른다.
“네, 말씀하세요” 안내 후 질문하면 말이 끝났을 때 자동 전송한다.
“시리, 바닐라라테 시럽 몇 펌프야?”처럼 한 번에 말해도 된다.
운영 점주·본사 계정은 답변을 읽은 후 다시 호출어를 기다린다.
예비 점주는 기존 정책대로 답변을 화면으로만 표시한다.
질문 입력 중 “취소”라고 하면 전송하지 않고 다시 대기한다.

기본값은 꺼짐이며 사용자가 직접 켜야 한다. 대기 중 음성도 브라우저 제공 인식 서비스에서
처리될 수 있으며, 인터넷과 마이크 권한 및 HTTPS/localhost가 필요하다.
음성 인식을 지원하지 않는 브라우저에서는 이 기능을 사용할 수 없다.
대기 끄기·Escape·탭 전환·화면 이탈 시 인식과 읽기를 중지한다.
API 요청이 이미 전송된 경우 서버 처리는 완료될 수 있지만 중지 후 자동 읽기는 하지 않는다.
음성 인식·답변 오류로 대기가 종료되면 화면을 확인한 후 직접 다시 켠다.

### 내 발음 등록

음성 대기를 끈 상태에서 **내 발음 등록**을 열어 “시리”만 3~5번 말한다.
매회 실제 인식된 표현을 확인하고 호출어로 사용할 표현에 체크한 뒤 저장한다.
최소 3회 수집과 1개 이상 선택이 필요하며, 저장된 표현은 이후 문장 앞 호출어로 인식한다.
기본 호출어도 계속 사용할 수 있다. 재등록하면 선택한 새 표현으로 대체하며 초기화도 가능하다.

녹음 파일이나 목소리 모델은 저장하지 않는다. 확인된 문자열만 현재 사이트의 localStorage에
계정·실제/시연 모드별로 분리해 저장한다. 다른 기기·브라우저·사이트 주소에는 동기화되지 않는다.
브라우저 저장을 차단하거나 데이터를 삭제하면 등록이 유지되지 않을 수 있다.
음성을 아예 알아듣지 못하는 경우에는 문자열 보정으로 해결되지 않는다.

음성 대기가 켜져 있으면 답변 재생 중에도 호출어를 듣는다. 다시 호출하면 현재 읽기를
중지하고 새 질문을 받는다. 호출어와 새 질문을 함께 말하면 바로 새 질문으로 전송한다.
기본 호출어와 저장한 개인 발음 모두 사용한다. 재생 중 인식을 지원하지 않는 환경에서는
안내를 표시하며 현재 답변은 계속 읽는다. 이 경우 대기 끄기 버튼으로 중지할 수 있다.
기기별 스피커·마이크 동시 사용과 스피커 소리 재인식 여부는 실제 기기에서 확인해야 한다.

호출어를 시리로 변경하면서 기존 v1 개인 발음 등록은 사이트에 다시 접속할 때 모든 계정에서 초기화한다. 새 등록은 v2 시리 전용 저장소를 사용하며 로그인·대화 데이터는 삭제하지 않는다.

## 확인 질문과 온도 후속 답변

서버가 `follow_up_questions`를 반환하면 본문에 이미 표시된 문구는 반복하지 않고
빠진 확인 질문만 추가한다. HOT/ICED 선택을 요청한 경우에는 활성 대화의 최신 답변에만
핫·아이스 버튼을 표시한다. 선택한 온도는 기존 `conversation_id`로 전송한다.
일반 확인 질문에는 클라이언트가 임의로 답변 선택지를 만들지 않는다.
예전 대화나 비활성 대화의 버튼으로 다른 대화에 후속 답변을 보내지 않으며,
이 변경은 기존 API 계약을 그대로 사용한다.
