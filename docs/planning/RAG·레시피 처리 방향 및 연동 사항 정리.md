[팀 공유] RAG·레시피 처리 방향 및 연동 사항 정리

**1. MVP 처리 방향**

- 레시피와 창업·운영 상담 모두 기존 **`/rag-query`**를 사용합니다.
- 공개·내부 응답 형식과 기존 계약 테스트는 유지합니다.
- 레시피 전용 RDB·별도 API·단계 전용 화면은 **E2E 이후 확장**으로 둡니다.
- 상담은 **LangChain + LangGraph 기반 단일 에이전트**로 구성합니다. 여러 전문 에이전트로 나누지는 않습니다.
- 첫 실제 상담 검증은 운영 점주의 **고객 불만·위생 질문**부터 진행합니다.

**2. 레시피와 상담의 답변 원칙**

| 구분             | 레시피 빠른 처리                    | 창업·운영 상담                 |
| ---------------- | ----------------------------------- | ------------------------------ |
| 먼저 보여줄 내용 | 질문한 계량·제조 단계               | 상황에 맞는 짧은 핵심 답변     |
| 상세 내용        | 필요한 재료·순서·옵션               | 확인·처리 순서, 적용 조건·예외 |
| 근거             | 메뉴·온도·판본·원문 위치            | 문서명·판본·페이지 또는 섹션   |
| 정보 부족        | 답이 달라지는 메뉴·온도·옵션만 확인 | 답변에 필요한 상황만 추가 질문 |
| 원칙             | 검수된 구조화 자료의 값·순서 유지   | 확보한 근거 안에서 설명        |

레시피는 A의 구조화 JSON을 조회해 정확한 값·단계를 반환하는 내부 경로를 연결합니다. 메뉴·옵션 해석과 실제 값 선택을 구분하고, 계량·단계를 LLM이 임의로 작성하거나 변경하지 않도록 합니다.

단계 질문은 직전 최대 6턴을 활용하되, “딸기 넣었어”만으로 메뉴나 완료 단계를 임의 확정하지 않습니다. 모호하면 짧게 되묻습니다.

**3. 속도에 대한 정리**

현재 규모에서 RDB 도입을 속도 개선의 필수 조건으로 보지는 않습니다. 전체 지연은 다음을 나눠 측정합니다.

- 요청 해석·구조화
- 질문 임베딩
- 검색·자료 조회
- 답변 생성

현재 B 구현은 기본적인 한 번 검색에서도 모델 호출이 여러 번 발생하므로, **모델 호출 수와 답변 재생성 축소를 먼저 검토**합니다.

레시피 JSON으로 답변 생성을 생략하더라도 요청 해석·임베딩 지연은 남을 수 있습니다. 기존에 언급된 2~5초 등은 실측·보장값으로 사용하지 않습니다.

**5. 데이터·백엔드 연결 기준**

- 레시피 시나리오는 **바닐라 시럽 20→15mL, 2026-10-26 00:00 KST 적용** 기준입니다.
- 구조화 JSON에는 기본 계량뿐 아니라 명시된 옵션·공통 규칙·미지원 사항·판본·원문 출처가 필요합니다.
- 미래·미배포 자료는 JSON에 존재하더라도 현재 답변에 노출하지 않습니다.
- JSON과 검색 조각이 같은 문서·판본을 가리키는지 확인하고, 실제 허용된 조각으로 `sources`를 구성합니다.
- `chunk_id`는 100자 이하이며, 긴 조문의 상위 섹션·분할 순서를 복원할 방법을 A/B가 맞춥니다.
- `index.faiss`의 벡터 순서와 `chunks.jsonl` 레코드 순서를 일치시킵니다.
- 본문 해시·임베딩 입력 구성·거리·정규화 방식은 A/B가 확정합니다.
- 임베딩은 `text-embedding-3-small` 1536차원이 **초기 제안**이며, A·B·E의 최종 합의와 실제 품질 검증이 필요합니다.
- C 방침에 따라 법령 시점 미검수 자료도 검색에 허용하되, B가 **“시행일 미검수”**를 표시합니다. A는 해당 문서·조각을 식별할 정보를 제공해야 합니다.
- 표 깨짐·추출 누락은 별도로 확인합니다. 미검수 표시를 붙였다는 이유로 부정확한 수치까지 정상 답변에 사용하지 않습니다.

C 회신 기준 연결 설정:

- JWT: `HS256`, `iss=frangizer`, `aud=frangizer-api`
- 클레임: `sub`, `role`, `brand_id`, `store_id`, `permissions`
- 공유 마운트: `/var/lib/frangizer`
- `DOCUMENT_STORE_DIR=/var/lib/frangizer`
- `FAISS_DIR=/var/lib/frangizer/faiss`
- 저장 키: `documents/{document_id}/{version_id}.pdf`
- 색인 상태 조회: `GET /internal/v1/index-jobs/{job_id}`

비밀값은 별도로 전달합니다. 실제 JWT 키 처리 방식과 역할별 null `store_id`, TXT·MD 저장 방식은 코드·연동 테스트에서 확인합니다.

색인 작업의 재시작 시 남은 `running`은 `failed + INTERRUPTED`로 처리하는 방향이며, 재승인·재색인은 C의 계약 보완 PR과 맞춥니다. B의 질의 중복 처리와 색인 작업 중복 처리는 별개입니다.

**6. 현재 상태와 다음 순서**

B는 로컬에서 질의 API·인증·LangGraph 흐름·출처 검증·재시도 처리를 구현했고, **오프라인 검사 41개가 통과**했습니다.

이는 실제 문서 검색·모델 상담 품질·백엔드 E2E 검증 완료를 의미하지 않습니다. 레시피 JSON 빠른 경로와 실제 색인 작업 연결도 아직 남아 있습니다.

다음 순서는 다음과 같습니다.

1. A·C의 실제 코드·PR과 산출물 확보
2. 첫 상담 문서 묶음의 검색·원문·출처 연결
3. 레시피 구조화 JSON과 기존 출처 형식 연결
4. 백엔드 → RAG → 화면 E2E 검증
5. 구간별 지연 측정 후 필요한 부분 최적화

평가 질문·정답·테스트용 자료는 운영 색인에 넣지 않습니다.
