## 2. 실행 방법

```bash
# 레시피 구조화 생성 + 원문 대조 (254개 항목)
python3 rag/app/indexing/recipe_structure.py          # --check: 대조만

# 상담 문서 로컬 검수: 추출·분할만, 임베딩·외부 호출 없음. 보고서는 저장소 밖에 생성
cd rag && python3 -m app.indexing.local_check --out /tmp/frangizer-quality

# 테스트 (가짜 임베더 사용, 네트워크 없음)
cd rag && python3 -m pytest tests/indexing -q
```

의존성은 `rag/requirements.txt`, 검사 도구는 `rag/requirements-dev.txt`로 통합했다. `rag/app/indexing/requirements.txt`도 같은 서비스 의존성을 참조한다. PDF는 PyMuPDF, 벡터 검색은 FAISS, 제공자 연결은 OpenAI SDK를 사용한다.

임베딩 환경변수: `EMBEDDING_MODEL=text-embedding-3-small`, `LLM_API_KEY`(계약 11.3 목록), 선택 `EMBEDDING_BASE_URL`. 64개씩 묶어 호출한다. 문서 색인은 429·5xx 등을 3회까지 재시도하고, 사용자 질문 임베딩은 재시도하지 않는다. 오류 메시지에 키·본문을 남기지 않는다.

## 3. 색인 작업이 하는 일 (`run_index_job`)

입력은 `IndexJobRequest`(계약 그대로, 추가 필드 거부)이고 반환은 `IndexJob`이다. 서버 시작 시 `JobStore(FAISS_DIR).recover_interrupted()`를 한 번 호출한다.

B 라우터 연결 (C 백엔드 PR #3 구현 기준):

```python
@router.post("/internal/v1/index-jobs", status_code=202)
def start(body: dict, tasks: BackgroundTasks):          # X-Internal-Token 검증은 B
    return {"data": run_index_job(body, background=tasks.add_task), "request_id": ...}
```

- 백엔드는 승인 시 한 번 보내고, 이후 작업 조회(프론트 2초 폴링)마다 **같은 job_id·같은 본문으로 다시 POST**해 현재 상태를 받는다(읽기 제한 25초). `background`를 주면 첫 응답은 바로 `queued`이고, 재전송에는 저장된 현재 상태가 돌아간다.
- 스키마 오류(`ValidationError`)를 422로 돌려주면 백엔드는 `UPSTREAM_ERROR`로 보고 작업을 queued로 둔 채 계속 재전송한다 — 오류를 작업 실패로 남길지 B·C 확인 필요.

경로 기본값(C 회신): 볼륨 하나를 backend·rag 모두 `/var/lib/frangizer`에 마운트한다. `DOCUMENT_STORE_DIR=/var/lib/frangizer`, `FAISS_DIR=/var/lib/frangizer/faiss`. 저장 키는 `documents/{document_id}/{version_id}.pdf`이다.

1. 저장 키 → `DOCUMENT_STORE_DIR` 안의 실제 파일. `..`·빈 구간·루트 밖 심볼릭 링크 거부
2. sha256 대조 → 불일치 `CHECKSUM_MISMATCH`
3. 쪽 정책 검증(범위 밖·포함/제외 충돌·남는 쪽 없음) → 추출 → 분할
4. 임베딩 → `FAISS_DIR/revisions/.tmp-…`에 작성 → 검증 → 이름 바꿔 확정
5. 같은 `job_id`+같은 내용은 기존 결과, 다른 내용은 `JobConflict`(→ 409)

`index_revision`은 판본·파일 해시·쪽 정책·분할 버전·임베딩 모델·차원·산출물 형식·메타데이터로 정해진다. 같은 입력은 같은 revision을 재사용하고 덮어쓰지 않는다. 하나라도 바뀌면 새 revision이 생긴다. 실패하면 임시 디렉터리를 지우고 기존 revision은 그대로 둔다.

### 실패 코드 (`IndexJob.error_code`)

계약은 `CHECKSUM_MISMATCH`만 명시한다. 아래 목록은 C가 채택했고(2026-10-23), 백엔드는 `error_code`를 그대로 전달한다.

| 코드 | 의미 |
| --- | --- |
| `CHECKSUM_MISMATCH` | 파일 해시가 요청과 다름 |
| `INVALID_STORAGE_KEY` / `SOURCE_NOT_FOUND` | 저장 키가 루트를 벗어남 / 파일 없음 |
| `PAGE_POLICY_INVALID` | 쪽 정책 오류 |
| `EXTRACTION_FAILED` | 열 수 없음·모든 쪽 스캔본·조각 0개 |
| `ARTICLE_PERIOD_CONFLICT` | 문서 적용일 전에 끝나는 조문이 생김 |
| `EMBEDDING_NOT_CONFIGURED` / `EMBEDDING_FAILED` | 모델 미설정 / 호출 실패 |
| `INDEX_VALIDATION_FAILED` | 건수·차원·해시·ID·판본 연결 검증 실패 |
| `INTERRUPTED` | 서버 재시작으로 중단(C 제안). C가 새 job_id로 재색인 |
| `INTERNAL_ERROR` | 그 밖의 오류(내부 경로는 남기지 않음) |

## 4. 연결된 산출물 형식

`FAISS_DIR/revisions/{index_revision}/`

| 파일 | 내용 |
| --- | --- |
| `index.faiss` | `IndexFlatIP`, L2 정규화 벡터. i번째 벡터 = `chunks.jsonl` i번째 줄 |
| `chunks.jsonl` | 줄마다 `{"metadata", "heading", "text", "section", "review"}` (아래) |
| `build-manifest.json` | 입력 해시·쪽 정책·분할 버전·모델·차원·정규화·임베딩 입력 규칙·건수·`chunk_ids` 순서 |
| `quality-report.json` | 쪽별 글자 수·제거한 머리말 수·표 수·경고 |

작업 기록은 `FAISS_DIR/jobs/{job_id}.json`. 단일 프로세스 가정이며, 재시작 시 `running`으로 남은 작업은 `failed` + `INTERRUPTED`로 바꾸고 남은 임시 디렉터리를 지운다.

`metadata`는 계약의 `IndexedChunkMetadata`만 담고(추가 필드 없음), 본문은 바깥 `text`에 둔다. 테스트에서 계약 YAML로 직접 검증한다. 예시: `docs/planning/examples/index-revision/` (테스트용 가짜 임베더로 만들어 `embedding_model`이 `test-fake-embedding`이고 벡터 파일은 넣지 않음).

### `chunks.jsonl` 한 줄 (B 요청 반영)

| 필드 | 내용 | B가 쓰는 곳 |
| --- | --- | --- |
| `metadata` | `IndexedChunkMetadata` | 허용 판본·적용 기간 필터, 출처 |
| `heading` | 조 제목(장 > 조) 또는 쪽 첫 줄 | 출처 표시 |
| `text` | 본문. **임베딩 입력 = 이 값 그대로**, `content_sha256 = sha256(text, UTF-8)` | 문맥 |
| `section.parent_section_key`·`part`·`parts`·`pages` | 나누기 전 섹션 키와 순서. 같은 parent의 1..parts를 이으면 원문 섹션. 나눈 조각 첫 줄은 `{제목} (이어서)` | 긴 조문 상위 조건·순서 복원 |
| `review.legal_temporal_reviewed` | 문서 단위 시점 검수 여부(지금 전부 false) | "시행일 미검수" 표시 |
| `review.period_source` | `document`(문서 적용일) / `future_trailer`(시행 예정 조문 꼬리표로 나눔) | 미래 조문 설명 |
| `review.temporal_note` | 자동 판단 못 한 조문별 시행일 표기 | 검수 필요 표시 |
| `review.quality_flags` | 조각이 걸친 쪽의 추출 표시 (아래 5장) | 수치 사용 여부 판단 |

거리: 벡터 L2 정규화 후 내적(= 코사인). 질문 벡터도 L2 정규화해야 한다.

### 조각 ID

| 필드 | 형식 | 예 |
| --- | --- | --- |
| `section_key` | 조 `art-{조}[-{의}]`, 부칙 `add{n}-art-…`, 쪽 `p{쪽}`, 나눈 경우 `.p{n}`/`.{n}`, 시행 예정본 `-from{YYYYMMDD}` | `art-12-2-from20261231` |
| `chunk_id` | `chk-{revision 일부 12자}-{section_key}`. 100자를 넘으면 section_key를 해시로 줄임(자르지 않음). 원본 14개 전체에서 100자 이하·중복 없음 확인 | `chk-3f2a…-art-17` |
| `article` | 원문 표기 | `제12조의2`, `부칙1 제1조` |
| `page` | 조각이 시작하는 PDF 파일 쪽(1부터) | `5` |

| 자료 | 분할 | 결과 |
| --- | --- | --- |
| 법령·고시 본문 | 조 단위, 긴 조는 항(①…) 경계에서 나누고 조 제목을 다시 붙임. 장·절 제목은 본문에서 빼고 조 제목 맥락으로 | 조문형 8개(식품위생법·시행령·시행규칙, 가맹사업법·시행령, 소비자기본법, 소비자분쟁해결기준, 전자상거래법 발췌) 조 단위 |
| 별표·지침·표 | 쪽 단위(1,500자 안팎에서 줄 경계로 나눔, `⇒` 짝 사이에서는 끊지 않음). 별표 파일의 부칙은 조 단위 | 심사지침, 두 별표 파일 |
| 정보공개서 | 쪽 단위 | 처리한 58쪽 중 40쪽에 표 |
| 합성 계약서 | 조 단위 | 53개 조 |
| 레시피 | 쪽(메뉴) 단위 | 8쪽 |

**시행 예정 조문 처리.** 법제처 출력본은 시행 전 개정 조문을 현행 조문 뒤에 다시 싣고 끝에 `[시행일: 2026. 12. 31.] 제12조의2` 같은 꼬리표를 붙인다. 그대로 색인하면 아직 시행되지 않은 조문이 현행처럼 검색된다. 꼬리표 기준으로 시행 예정본은 그 날부터, 앞의 현행본은 그 날까지로 조각 적용 기간을 나눴다. 현행본 없이 조 전체를 가리키는 꼬리표는 시행 예정 신설 조문으로 본다.

| 문서 | 자동 분리한 조문 |
| --- | --- |
| 식품위생법 | 28 |
| 가맹사업법 | 9 |
| 가맹사업법 시행령 | 3 |
| 식품위생법 시행령 | 2 |

`legal_temporal_reviewed`는 전부 `false`다. 위 처리는 출력본 표기를 기계적으로 읽은 것이며 경과규정·부칙 검토를 대신하지 않는다. C 결정(2026-10-23): 자동 분리 방식을 채택하고, `false`여도 검색을 허용하되 B가 답변에 "시행일 미검수"를 표시한다.

**표 (첫 상담: 고객 불만·위생).** 소비자분쟁해결기준 별표의 `분쟁유형 | 해결기준 | 비고` 표는 일반 텍스트로 뽑으면 칸 단위로 나와(분쟁유형 전부 → 해결기준 전부) 어떤 유형에 어떤 기준인지가 순서로만 남는다. 예를 들어 외식업(122쪽) "약정이용시점부터 1시간 전 이후 계약해제 → 예약보증금의 25% 환급"이 짝을 잃는다. 그래서 줄 좌표로 같은 높이의 행끼리 짝지어 다시 쓴다.

```text
- 약정이용시점부터 1시간 전 이후 계약해제
⇒ ㅇ 예약보증금의 25% 환급
…
[비고]
* 예약보증금은 일반음식점의 …
```

원문 글자는 바꾸지 않고 `⇒`·`[비고]` 표시만 더하며, 짝지은 결과의 글자 구성이 원문과 다르면 원래 추출로 되돌린다. PyMuPDF 표 셀 추출은 쉼표·마침표가 칸 사이로 밀려(예: 정보공개서 `68272\n,`) 쓰지 않는다.

| 쪽 표시 (`review.quality_flags`) | 의미 | 해당 |
| --- | --- | --- |
| `table_rows_paired` | 행 짝짓기 완료, 글자 대조 통과 | 분쟁 별표 126쪽 |
| `table_needs_review` | 표가 있으나 구조 미보장. **수치는 원문 확인 없이 정상 답변에 쓰지 않는다** | 정보공개서 40쪽, 분쟁 별표 16쪽(품목 목록 등), 합성 계약서 2쪽 |
| `table_values_in_structured_recipe` | 레시피 재료표. 값은 구조화 JSON(원문 대조 완료)에서 가져온다 | 레시피 7쪽 |
| `table_pairing_mismatch` | 짝짓기 결과가 원문과 달라 원래 추출 사용 | 현재 0쪽 |

스캔본으로 보이는 쪽은 없다.

## 6. 레시피 구조화 자료

메뉴 7종, 메뉴·온도·판본 14건, 공통 규칙 12개. 값·단위는 원문 문자열 그대로이고 단위·펌프 환산을 하지 않았다. 원문 대조 254건 통과.

B 요청(기본 계량 + 명시된 옵션·공통 규칙·미지원 사항·판본·원문 출처) 반영:

| 필드 | 내용 | 예 (바닐라라테 ICED 1.1) |
| --- | --- | --- |
| `ingredients` · `steps` | 재료(순서·값·단위)와 단계 원문 | 바닐라 시럽 15 mL |
| `order_rules.options` | 원문에 값이 적힌 옵션. `set`은 그 옵션일 때의 재료량 | 덜 달게 → 바닐라 시럽 10 mL(펌프 2회), 시럽 빼기 → 0 mL, 얼음 적게 → 얼음 g |
| `order_rules.pumps` | 원문에 적힌 펌프 횟수만. 재료표 값과 다르면 생성 실패 | 15 mL = 펌프 3회 |
| `order_rules.constraints` | 미지원·금지·기준 없음 | "줄어든 시럽량을 다른 재료로 보충하지 않는다" |
| `order_rules.info` | 그 밖의 안내 | "HOT과 ICED에 동일하게 적용한다" |
| `common_rules` | 12개 규칙 + 종류(basis·option·unsupported…) + 값 있는 공통 옵션(샷 추가 +30 mL) | 08 대체유 → unsupported |
| `sources[]` | `document_id`·`version_id`·파일 쪽·인쇄 쪽 | `demo-cafe-recipes-1.1`, 5쪽 |

얼음 옵션은 얼음이 있는 온도에만 붙인다(아메리카노 HOT에는 없음). 딸기라테 HOT처럼 없는 조합은 레코드가 없고, "HOT 제조는 지원하지 않는다"가 `constraints`에 있다.

**노출 조건.** 파일에 있다는 것만으로 답변에 쓰지 않는다. `sources[].version_id`가 질의의 `allowed_versions`에 있고 `effective_from ≤ as_of < effective_until`이어야 한다(v1.1은 staged). 이 `version_id`는 같은 판본 PDF 조각의 `metadata.version_id`와 같아서, 검색된 조각과 JSON 레코드가 같은 판본인지 대조할 수 있다. 내용이 바뀐 메뉴만 새 판본 건을 만든다(바닐라라테 HOT·ICED 20→15 mL, 허니자몽블랙티 v1.1 신규). PDF 줄바꿈 자리의 띄어쓰기는 텍스트로 알 수 없어 11곳을 사람이 검수해 3곳만 띄웠다(`review.wrap_joins`).

이 자료는 현행 시나리오(20→15 mL, 2026-10-26 0시)를 따르며, C가 이 시나리오에 동의했다. 이전 합성 데이터(20→25 ml, 메뉴 50종)는 쓰지 않는다.

**쓰임(C 회신).** MVP에서 레시피도 `/rag-query`로 답하고 RDB 적재는 하지 않는다. 조리 중 단계·양 질문의 응답 속도가 문제되면 B가 RAG 내부에서 이 파일로 LLM 없이 답할 수 있다. 응답 형식·출처는 그대로라 백엔드·화면은 바뀌지 않는다. 연결할 때 쓰는 키는 다음과 같다.

- 검색된 레시피 조각의 `page`(PDF 파일 쪽)와 판본 → `recipe_versions[].sources[]`의 `document_version`·`page`
- 질의 시점 → Java의 허용 판본과 색인 조각의 적용 기간. JSON의 예정일만으로 배포 중인 이전 판본을 만료시키지 않음
- 메뉴·온도 → `menu_id`·`temperature`. 직전 6턴 대화로 "아까 그 메뉴"를 해석하는 것은 B 몫이다.

## 6-1. 표 JSON (정보공개서)

B의 답변 단계는 근거 조각에 `table_needs_review`가 있으면 답변을 "표 검수 필요" 한 줄로 바꾼다. 팀 결정(2026-10-23): 사람 검수·외부 API 없이, Claude가 표를 읽어 JSON으로 만들고 색인 때 행 문장으로 붙인다.

- 파일: `data/structured/table_transcriptions.json`, 모듈 `rag/app/indexing/table_transcription.py` (rag 컨테이너는 `RECIPE_STRUCTURED_FILE`과 같은 폴더에서 읽음, 따로 지정은 `TABLE_TRANSCRIPTION_FILE`). `table_reviews.json`·`table_review.py`·`tables.py`는 다른 팀원의 표 후보 추출·승인 기능이며 별개 형식이다(2026-10-23 머지 충돌로 두 파일이 섞였던 것을 분리)
- 범위(원본 sha256별): 빽다방 정보공개서 71개, 소비자분쟁해결기준 별표 18개(분쟁유형 표 126쪽은 행 짝짓기), 합성 가맹계약서 2개, 식품위생법 시행규칙 6쪽·가맹사업법 시행령 별표 2쪽(표로 잡힌 본문 줄 — 데이터 표 아님)
- 결과: 원본 14개 문서 전체에서 `table_needs_review` **0쪽**. `table_reviewed` 73쪽, `table_rows_paired` 126쪽, 레시피 `table_values_in_structured_recipe` 7쪽
- 만드는 법(`source`)
  - `draft:geometry`: 칸 테두리 좌표로 만든 초안. 병합 칸은 행마다 채우고, 두 줄 머리글은 위 칸 이름을 앞에 붙이고, 쪽 경계 표는 앞 쪽 머리글을 이어받음. 자동 검사(값·머리글 원문 대조, 결과에 안 들어간 칸 없음, 한 칸에 상자 하나, 합계)를 통과한 것만
  - `claude:image`: 초안이 실패한 표는 쪽 이미지를 보고 옮겨 적음. 칸 내용은 원문 텍스트 조각을 그대로 씀
  - `claude:image(가로선 행 나누기·줄 높이 짝짓기)`: 칸 안에 여러 항목이 줄 단위로 든 표(분쟁 별표 2~6쪽 품목 목록, 142~144쪽 품질보증기간). 페이지에 그려진 가로선(점선 포함)이나 같은 높이의 줄로 행을 나누고, 원문 줄이 빠짐없이 들어갔는지 확인
- 색인 때 모든 값·제목·열 이름이 원문에 있는지 다시 확인하고, 맞지 않으면 그 표는 적용하지 않음
- 표 후보 영역 분리(`extract.separate_table_regions`)가 된 쪽: 설명 글은 `pN.prose` 조각, 옮겨 적은 표는 표마다 `pN.tableK` 조각(제목·단위 포함, `table.engine=table_transcriptions`). 그 쪽의 자동 추출 표 후보는 쓰지 않음. 분리가 안 된 쪽은 쪽 본문 앞에 `[검수된 표 · PDF 원본 대조]` 행 블록. 답변에 별도 안내는 붙이지 않음(팀 결정)
- 원문 줄 순서만 확인한 쪽(rows 없음)은 영역 분리를 취소하고 원래 쪽 본문을 씀
- 기록 파일을 읽지 못해도 색인은 계속하고 품질 보고서에 `TABLE_TRANSCRIPTION_UNREADABLE`
- 원본 sha256에 묶임. JSON이 바뀌면 `index_revision`이 바뀌므로 다시 색인해야 반영됨(시연 환경: `docker compose down -v` 후 시드)
- 확인: 사람이 대조한 표(19·20·21·24·25·49쪽)와 칸 좌표 초안을 비교했을 때 틀린 짝 0. 7쪽 재무표, 11쪽 지역별 가맹점 수, 12쪽 연도별 가맹점 수·특수관계인 가맹사업, 14쪽 평균 매출액, 31쪽 메뉴 권장가격은 쪽 이미지와 값을 대조함

조문 시점 검수 기록(legal_reviews.json)은 팀 결정으로 넣지 않는다. 법령 답변의 `[시행일 미검수]`는 B 표시 그대로다.
