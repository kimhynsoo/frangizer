**3. 레시피 구조화에 추가로 필요한 내용**

재료표·제조 단계만으로는 주문 옵션 질문을 처리하기 어렵습니다. 다음 내용을 함께 준비해 주세요.

- **식별:** 메뉴 ID·표시명·별칭, HOT/ICED, 1잔 기준과 컵 규격
- **계량·순서:** 원문 계량 문자열·단위·재료 순서·제조 단계
- **옵션:** 기본·덜 달게·시럽 빼기·얼음 적게/없음·샷 추가의 승인된 값 또는 명시 규칙
- **공통 규칙:** 옵션 적용 시 다른 재료를 유지하는지, 어떤 재료에 펌프 기준을 적용하는지
- **미지원 사항:** 미등록 온도·대체유·품절 대체·등록되지 않은 메뉴
- **판본·출처:** 레시피 판본과 문서 판본의 연결, 배포 상태·적용 기간, 원본 파일·PDF 쪽·인쇄 쪽

특히 바닐라 전용 펌프 기준을 초콜릿 소스 등에 적용하면 안 됩니다. 없는 환산·대체 기준도 만들지 않습니다.

초기에는 **원문에 명시된 옵션별 값을 검수해서 저장하는 방식**을 우선 제안합니다. 공통 규칙을 원문 텍스트로만 보존한 경우, 어떤 부분을 자동 처리할 수 있는지 별도로 표시해 주세요.

`amount`는 원문 표시값을 보존하고, 계산이 필요하다면 검증된 숫자값을 별도로 둘 수 있습니다. 자유 문장을 숫자로 억지 변환하지 않습니다.

변경 없는 레시피는 여러 문서 판본과 연결해 재사용할 수 있습니다. 다만 새 문서가 미배포이거나 적용일 전이라는 이유로 신규·변경 계량이 먼저 노출되지 않아야 합니다. 적용 기간 종료는 **종료 시각 미포함**으로 통일하고, 기존 판본이 만료됐는데 새 판본이 미배포라면 구판을 조용히 재사용하지 않는 정책도 C와 정해야 합니다.

**4. 상담 검색 산출물에서 맞출 세부 규칙**

- `index.faiss`의 i번째 벡터와 `chunks.jsonl`의 i번째 레코드를 대응시킵니다. 건수·순서·차원을 검증해 주세요.
- JSONL은 A가 제안한 `metadata`, `heading`, `text` 구성을 기본으로 합니다.
- `content_sha256`은 **파싱한 `text` 문자열의 UTF-8 SHA-256**으로 통일 제안합니다. `heading`이나 JSONL 한 줄 전체의 해시와 구분합니다.
- 임베딩 입력이 `text`인지 `heading + text`인지, 결합 방식까지 생성 보고서에 기록해 주세요. 모델·차원·거리·정규화도 기록합니다.
- ID는 사람이 읽기 쉬울 필요보다 **유일성·길이·계약 패턴 준수**가 중요합니다. 예시 ID를 그대로 만들 필요는 없습니다.
- 긴 조문을 나눌 때 상위 섹션과 조각 순서를 복원할 수 있어야 합니다. 현재 RAG는 동일 `section_key`를 기준으로 복원하므로, **상위 섹션 키를 공유하고 조각 ID에서 분할을 구분하는 방식**을 우선 제안합니다.
- 복원 과정에서도 판본·인덱스·권한·적용 기간을 유지합니다.
- 한 번에 반환할 자료량과 잘림 표시도 합의합니다. 현재 RAG 기본 제한은 배치당 최대 20조각·12,000자입니다.

`TABLE_NEEDS_REVIEW`, 법령 시점 미검수, 추출 누락은 **어떤 페이지·조각에 해당하는지** 품질 보고서에서 연결할 수 있어야 합니다. 기존 메타데이터 스키마에 임의 필드를 추가하지 않고 전달 방식을 맞춥니다.

미검수 자료는 개발 단계의 검색 확인과 시연 정답 사용을 구분합니다. 시연에 쓰는 핵심 표·조문은 검수하고, 확인되지 않은 부분은 확정된 답으로 제시하지 않습니다. 시행 예정 조문 자동 분리와 별표 적용일 판단도 검수 완료로 취급하지 않습니다.

**8. C 회신 후 B의 추가 대조 항목**

- JWT: HS256, `iss=frangizer`, `aud=frangizer-api`, `sub`·`role`·`brand_id`·`store_id`·`permissions`. 현재 B는 환경변수로 이 값을 설정할 수 있습니다. 실제 키 바이트의 UTF-8/Base64 처리, hq/prospect의 null `store_id` 표현을 역할별 테스트 토큰으로 확인합니다. 비밀값을 문서·커밋에 적지 않습니다.
