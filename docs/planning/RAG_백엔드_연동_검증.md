# RAG·백엔드 연동 구현 및 검증

작성일: 2026-10-23 · 작업 브랜치: `feat/rag-counsel-api`

현재 원격 main의 Java·웹 코드와 A의 `feat/rag-indexing-pipeline`을 로컬 작업 브랜치에 병합해 연결했습니다. 원격 main에 이번 RAG 변경을 반영한 상태는 아닙니다. API 계약 파일은 수정하지 않았습니다.

## 구현된 부분

- Java 원 사용자 JWT를 HS256, UTF-8 원문 키, issuer `frangizer`, audience `frangizer-api`로 재검증합니다. JJWT가 배열로 발급하는 aud와 본사/예비 점주의 생략된 null store_id를 지원합니다. 점주는 점포 ID가 반드시 일치해야 합니다.
- `POST /internal/v1/index-jobs`: 인증·입력 검증 후202, 비동기 색인. 같은 ID·같은 본문은 기존 상태, 다른 본문은409입니다. 현행 C의 POST 폴링을 유지합니다.
- `GET /internal/v1/index-jobs/{job_id}`: 같은 작업 상태를 반환합니다. 없는 작업은404입니다. C가 후속 PR에서 GET으로 전환할 수 있습니다.
- 재시작 시 남은 queued/running 작업은 failed + `INTERRUPTED`로 처리합니다. 새로운 작업 ID로 재요청해야 합니다. 색인 실행은1개, 대기 포함16개, worker는1개입니다.
- A의 revision 산출물을 읽고, 브랜드·visibility·허용 판본·조각 적용일 제한을 순위 계산 전에 적용합니다. 모델·차원·정규화 방식·매핑·본문 SHA256도 검사합니다.
- 문서/질문이 같은 OpenAI 임베딩 어댑터를 사용합니다. 모델은 환경변수에 명시하며 실제 제공자 호출 코드는 구현했지만 이번 검증에서는 호출하지 않았습니다. 차원을 바꾸면 재색인이 필요합니다.
- 공식 자료의 시행일 검수가 끝나지 않았다면 답변에 `[시행일 미검수]`를 붙입니다.
- 구조화 레시피 파일을 설정하면 명확한 단일 메뉴·기본1잔의 계량/단계를 LLM 없이 반환합니다. 원본 SHA256·허용 판본·쪽·본문과 맞아야 합니다. 요청한 양이 HOT/ICED에서 같으면 공통 값을 바로 반환하고, 답이 달라지는 온도/완료 단계는 되묻습니다.

## 실제로 확인한 것

- RAG 자동 검사 **93개 통과**, 이 중 실제 Java JwtService가 발급한 점주·본사·예비 점주 JWT 검사3개 포함.
- 백엔드 `./gradlew test` 통과. 이 검사는 C가 작성한 H2+목 RAG 테스트입니다.
- 별도 실제 HTTP 검사: **Java + H2 + FastAPI + 실제 합성 PDF 추출 + FAISS 생성/로딩 + 구조화 레시피 응답**.
- HTTP 확인 흐름: 로그인 → 업로드 → 승인 → 색인 → POST 폴링 → 배포 → 점주/본사 질문 → `20 mL`, 출처5쪽 → 같은 요청 결과 재사용. 예비 점주의 레시피 접근 차단.
- 테스트에서 staged v1.1을 명시적으로 업로드·승인·배포한 뒤, 2026-10-26 00:00 KST 전후 **20 mL/v1.0 → 15 mL/v1.1** 전환 확인.
- JSON의 예정일만으로 기존 레시피를 만료시키지 않습니다. v1.1이 아직 배포되지 않아 Java가 v1.0을 허용한다면 v1.0을 사용합니다.

HTTP 검사의 임베딩은 테스트 대역이며 LLM 호출은 금지했습니다. 실제 임베딩의 검색 품질·LLM 상담 품질·MariaDB·브라우저 E2E를 통과했다는 의미는 아닙니다. 실행 명령은 `rag/README.md`에 있습니다.

## 담당자별 연결 사항

| 담당 | 전달 사항 |
|---|---|
| A 데이터 | 산출물 포맷은 그대로 사용합니다. 공동 연결부인 embedding.py에 제공자 연결, job.py에 예약 작업 실행·차원 포함 revision·0벡터 거부를 보완했습니다. JSON의 source hash·판본·쪽과 indexed PDF 본문을 대조합니다. draft 원문의 온도별 대응·옵션 의미·표 구조 검수는 계속 필요합니다. |
| C 백엔드 | 현재 POST 폴링과 후속 GET 조회 모두 준비됐습니다. 새 공개 레시피 API/RDB는 없습니다. source 메타데이터 덮어쓰기와 allowed_versions 검증은 기존대로 유지합니다. 실패 판본 재승인·STT·429는 C의 후속 범위입니다. |
| D 프론트 | 응답 계약은 같습니다. 레시피 양은 answer, 제조 순서는 steps, 확인 질문은 follow_up_questions입니다. needs_review 상태에서 답이 확정된 것처럼 표시하지 않습니다. |
| E 통합 | 실제 서버 팩토리는 `app.bootstrap:create_service`입니다. root .env와 공유 볼륨을 주입합니다. backend/RAG의 DOCUMENT_STORE_DIR를 일치시키고 FAISS_DIR 및 결과 SQLite도 지속 볼륨에 둡니다. worker=1입니다. |

## 남은 검증과 범위

1. 실제 `.env`의 모델/임베딩 설정을 주입하고 승인 문서를 실제 임베딩으로 색인합니다. 테스트 산출물을 실제 FAISS_DIR로 복사하지 않습니다.
2. 기존 고객 불만·운영 지침 질문으로 출처 적합성, 추가 질문, 답변 보류, 모델 호출 수·구간별 지연을 평가합니다. 아직 실제 응답 시간 목표를 달성했다고 주장하지 않습니다.
3. MariaDB·프론트와 연동해 브라우저 E2E를 확인합니다.
4. 문서 상세 sections에 필요한 새 내부 API는 계약 합의 후 추가합니다. 이번에 임의 경로를 만들지 않았습니다.
5. 긴 조문의 다른 분할 조각을 자동 확장하는 기능과 다중 worker/복제본 작업 저장소는 후속 범위입니다.

레시피 전용 RDB·별도 API·단계 전용 화면은 기존 합의대로 MVP E2E 이후 필요성을 판단합니다. 분명한 계량/순서 질문에 생성 호출을 생략하는 현재 구현은 저장소 종류 변경보다 모델 호출 지연을 직접 줄이는 방식입니다.
